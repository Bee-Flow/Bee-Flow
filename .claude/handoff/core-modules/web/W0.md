## Verify first (before you build on them; each is a small throwaway probe, report what you saw)

1. **The golden normaliser.** The inventory tests read the shell with the TypeScript compiler
   (`agent-hub/src/test/guiInventory/sourceAst.ts`, `pages.ts`, `ownership.ts`). When
   `lazy(() => import('./X'))` becomes `moduleScreen('learning:LessonPlayerHost')`, the recorder
   must resolve the lookup, through the module's area file, to the same tree path and owner, so
   the golden stays byte-identical. Prototype it on `AuthedApp.tsx` (the lazy imports around
   lines 24-57) and `components/admin/Studio/studioRegistry.tsx:29`. Add a negative test: a
   lookup that names a different file changes the recorded entry.
2. **Hide mode refuses.** With `BEEFLOW_HIDE_MODULES=learning`, a static import, an `import()` and
   an `import.meta.glob` of a learning-owned file each fail the build with a message that names
   the file and the module (as `server/modules/roots/resolveHooks.cjs` does on the server).
3. **A zone keeps rendering synchronous.** Convert the settings boundary to `lazyZone` in a probe:
   a part provided statically by an area file of that zone is in the DOM on the first commit
   under React Testing Library (no Suspense fallback in between), and the chunk list of
   `node scripts/web-build-sources.mjs --report` differs only by the area chunk.
4. **Contexts have defaults.** `moduleWrap` renders only the children when the module is absent:
   list every core consumer of the contexts behind the four wraps (RecorderProvider,
   CaptureProvider, ProjectCaptureProvider, ProjectLiveProvider) and whether its `useContext`
   survives without the provider. Report the ones that do not; do not fix module files.

## Build

- `agent-hub/src/moduleHost/` (core): `contract.ts`, `registry.ts` (the only importer of
  `virtual:beeflow/*`, held by an eslint rule or a test), `index.ts`, `lazyZone.ts`,
  `loadModuleChunk.ts`, `ModuleBoundary.tsx`, `ModuleNotInstalled.tsx`, `ModuleUnavailable.tsx`,
  `ids.generated.ts` (from `scripts/module-map.json`, with a `--check` in `check:fast`'s reach),
  `owners/` and `exports/` (empty tables and interfaces that the later slices fill),
  `testing.ts` (`withModules({ id: 'absent' | 'failed' | 'loaded' })`, `mockModulePart`).
  The accessors and their absent answers are in DESIGN.md A2; keep the signatures.
- `agent-hub/vite/beeflowModules.mjs`: the plugin (DESIGN.md A3 a, c, e; the tree-path resolver
  over several roots (d) and the i18n virtual module (b) are later slices: leave clearly marked
  seams, not half an implementation). Registered in `vite.config.js` and used by vitest.
- The 23 ownership globs `src/firstParty/<id>{,.*}.{ts,tsx}` in `scripts/module-map.json`.
- The i18n namespace `modules` (English in `server/i18n/defaults/en/modules.js`, Dutch in
  `server/i18n/defaults/nl/modules.json`, then `npm run i18n:gen`): the texts of the two
  screens. Plain words: "This part of Bee Flow is not installed here." No upgrade text.
- `utils/lazyWithReload.ts`: the reload flag is cleared only after the same importer has loaded;
  a test with an importer that always rejects shows at most one reload.
- Run-time state: `bootModules()` reads the server's answer. The server side is another task;
  until it lands, `bootModules` treats a missing answer (404, error, 3 s) as "every built module
  is loaded", which must stay the behaviour for an old server anyway. Wire it where DESIGN.md
  A4 says (`AppRoutes.tsx`, in parallel with the AuthedApp chunk), and in `src/test/setup.ts`.
- **One key end to end**: `learning:LessonPlayerHost` (the lazy import in `AuthedApp.tsx`), with
  `src/firstParty/learning.hub.tsx` (or the zone that hosts it: say which and why) providing it.
