## Verdict: CHANGES REQUIRED

The stream half is correct and is the fix for the production symptom (aborted video range
requests no longer keep S3 bodies and their sockets checked out). The S3 timeout half does
not do what the commit message, the code comment and the issue say: in the installed
handler version `requestTimeout` is not a socket idle timeout and, by default, does not
abort anything. A stalled storage call still holds its socket indefinitely.

## What holds

- **Coverage.** All 17 `.pipe(res)` calls are replaced (approvals 2, formPublic/session 1,
  cmsAssets 1, evidence 1, sbom 1, storageProxy 2, studioAppFiles 2, studioAppPublic 1,
  templates 3, transcriptions/audio 3). No `.pipe(res)` is left in `server/` outside
  comments. The other `streamFile` consumers buffer with `for await`, which destroys the
  source on early exit.
- **Headers, status, Range.** The diff only swaps the pipe line (plus imports and the
  `fs` hoist in `templates.js`). Every `setHeader`, `res.status(206)`, `Content-Range` and
  `Content-Length` still runs before the stream starts, in the same order. The 416 path in
  `cmsAssets.serveAsset` and both 206 paths in `transcriptions/audio.js` are unchanged.
- **Authorization.** No auth, permission, token, org or ownership line moved. Every check
  still runs before `streamFile`, and the `sendStream` call is the last statement of each
  branch where the pipe used to be.
- **Errors after headers.** Verified with a scratch Express app plus the real
  `terminalErrorHandler`: a source error before the first byte, a source error mid-body,
  and a premature source close all end with a reset socket and no crash or second
  response. `pipeline` destroys `res` before it calls back, so `next(err)` reaches the
  terminal handler, which logs the 500 and its `res.json` on the destroyed response is a
  no-op.
- **onError vs the old `.on('error', next)`.** Same routing (`next`) for the routes that
  had it. One difference: an error before the first byte used to produce a 500 JSON body
  and now gives a connection reset, because `pipeline` destroys `res` first. That is
  acceptable: `GetObject` failures such as NoSuchKey surface from `s3.send`, before the
  stream exists, and keep their 404 paths. Routes that had no error listener at all
  (cmsAssets, storageProxy, templates, evidence, local audio) used to crash the process
  with an unhandled `'error'` event on an upstream failure; now they reset that one
  response. That is an improvement.
- **One shared client.** `storageStore.init()` builds the single `S3Client` from
  `s3ClientConfig`; no second client is created.
- **Pool.** The plain-object `requestHandler` form is honoured in this version
  (`NodeHttpHandler` builds `http(s).Agent({ keepAlive, maxSockets, ...httpAgent })` from
  a plain object), so `maxSockets: 100` takes effect; the test confirms it.
- **Typing.** Both new source files carry `// @typecheck` and pass the typecheck.

## REQUIRED

1. **`server/stores/storageClientConfig.js:9-11, 20`, severity High: `requestTimeout` does
   not bound a stalled request in `@smithy/node-http-handler` 4.12.1.**
   In this version `requestTimeout` is a wall-clock timer for "request written + response
   headers received". With the default `throwOnRequestTimeout: false` it only prints a
   warning (straight to `console`, outside `telemetry/log`). It never destroys the request.
   It is also cleared as soon as headers arrive, so it never covers the body. The real idle
   timer is `socketTimeout`. Checked against a scratch HTTP server, with the installed SDK,
   on a 1.5 s setting:
   - `requestTimeout`: a GetObject whose server stops after the headers stays open past
     4 s with no error. A GetObject whose server never answers is still pending after 4 s,
     with only a WARN printed.
   - `socketTimeout`: the stalled body errors (`ECONNRESET aborted`) at 1.5 s. The stalled
     request rejects with `TimeoutError` at 1.5 s.

   So the "every storage call waits without end" class from the issue is still open for a
   storage backend that stalls rather than resets. Only the client-abort leak is fixed.
   The mediaDims probe timeout in #223 relies on this too (see BUG-223 F2).

   **Fix:** set `socketTimeout: num('STORAGE_SOCKET_TIMEOUT_MS', 60000)` (true idle time).
   A long download that keeps moving continues. Multipart clip uploads send 16 MB parts
   per request, so an upload that keeps moving is never idle. Then either drop
   `requestTimeout` or keep it warn-only with a much larger value. Do NOT set
   `throwOnRequestTimeout: true` with 60 s: that turns it into a wall-clock limit that
   would kill slow single-PUT uploads and slow part uploads. Correct the comments in the
   file header and in the commit text (`STORAGE_REQUEST_TIMEOUT_MS` is described as an
   idle time, which it is not). Keep `connectionTimeout` as it is; that one does destroy
   the request.

2. **`server/stores/storageClientConfig.test.js`, severity Medium: the test asserts the
   config values, not the behaviour,** which is how F1 got through. Add a behavioural test
   against a local `http.createServer` that answers GetObject headers and then stalls.
   Build the client from `s3ClientConfig` with a small env override
   (`STORAGE_SOCKET_TIMEOUT_MS=300`) and assert that the body errors within about 1 s. A
   second case, a server that never answers, should assert a `TimeoutError`.

## Not required (worth a follow-up)

- `server/core/http/sendStream.test.js`, second test: `assert.ok(seen)` passes for any
  status and for `'err'`, so it does not prove that `onError` was called. Assert on a flag
  set inside `onError`, and assert that `ERR_STREAM_PREMATURE_CLOSE` does not reach it.
- After F1, a client that pauses a video (backpressure) for longer than the idle timeout
  causes an upstream `aborted` error, and `next(err)` logs it as a 500 on every such
  pause. If that turns out noisy, have `sendStream` skip `onError` when `res.destroyed`
  or `res.writableEnded` is already true and the error is an upstream reset.
- `formPublic/session.js` keeps its own `stream.on('error', next)` and calls `sendStream`
  without `onError`. That works, but it is the only route written that way; pass the
  handler to `sendStream` like the others.
- HEAD on `/api/cms/asset/*` still reads the whole object from storage (Node discards the
  body for HEAD). This predates the change, but for videos it is wasted pool time.
  Answering HEAD from `headFile` would avoid it.
