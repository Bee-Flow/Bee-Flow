# Review BUG-218: CMS MCP uploads hang, ticket burned

Commit 7cac6fa42 (worktree `Bee-Flow-wt/bug-W`), files `server/cms/mcp/uploadReceiver.js`,
`server/cms/mcp/uploadTickets.js`, plus tests.

Tests: `node --test cms/mcp/uploadReceiver.test.js routes/mcpCms.test.js`: 57/57 pass.

## Verdict: CHANGES REQUIRED

The hang is fixed (every wait now ends, the PUT always answers, the stuck 'uploading' state
is reported). Release is atomic (`kv.mutate`), happens only from 'uploading' with no asset,
and is bounded. The concurrency guard holds: a released ticket is burned again by the next
PUT, so two PUTs never run at the same time on one ticket. The access re-check, the
content-type bind and the size cap run again on every attempt because each retry goes
through the full `handle()`. Error bodies carry no internal detail (`err.message` goes to
the log only). Temp dirs are removed in `finally` on every path.

One real problem remains. A storage call that times out keeps running and gets a new random
key on every attempt, so one ticket can leave several stored objects.

## Findings

1. **uploadReceiver.js:233, 246, 267: a timed-out storage call is not cancelled, and each
   attempt gets a new key. Result: orphan objects, and one ticket can store more than one
   file. Severity: Medium (correctness and storage use; no privilege gain).**
   `withDeadline` only stops waiting: `streamIntoStorage` / `storage.uploadFile` keep running.
   `mediaHandlers.js:59` issues tickets without a `key`, so `bound.key` is undefined and
   `assetKeyFor()` picks a new `cms/<ts>-<rand>-…` key on every attempt. When a slow store
   finishes after the 504 and release, its object stays in storage under a key that no
   ticket records. `cms_list_assets` lists `cms/` keys, so it shows up in the asset library.
   The client's retry then stores a second copy under another key. Up to 4 attempts
   (1 + MAX_RELEASES), each up to `maxSize` (500 MB for clips), can leave 4 objects from one
   ticket. That breaks the one-ticket-one-file guarantee in its header comment. For a clip,
   the late part of the multipart upload also reads a temp file that `finally` has already
   unlinked. On Linux the open fd keeps it readable; if the open has not happened yet it
   fails and the multipart is aborted, which is fine.
   Fix (both parts):
   (a) Fix the key per ticket: derive it once, at `issue()` or the first `burn()`, store it on
   the record, and use it on every attempt. A late completion and a retry then write the same
   object, which is idempotent: no orphan, at most one asset per ticket.
   (b) Pass an `AbortSignal` into `streamIntoStorage` / `uploadFile` and abort it on the
   deadline. Stop between parts, then `abortMultipartUpload`. If the storage layer cannot
   take a signal, at least do not release on `StoreTimeoutError`. Mark it failed, or let the
   late completion call `finish(done)` itself, so a retry cannot run alongside a store that
   is still in flight.
   Test: storage that resolves after the deadline, then a retry. Assert one key in storage
   and that the ticket's asset key equals it.

2. **uploadReceiver.js:72 (`STORE_MS = 120 s` for every type): the store deadline does not
   scale with size. Severity: Medium.** A legitimate 500 MB clip needs more than about
   4.2 MB/s to object storage to finish in 120 s. Below that, a healthy upload times out
   every time and, through finding 1, leaves an orphan on each retry. Fix: a deadline that
   grows with size (for example a base plus per-MB time, capped), or a per-part idle deadline
   for the multipart path instead of one total deadline.

3. **uploadReceiver.js:117-118 (`arm()` on every `data` event): no overall deadline on the
   body of its own. Severity: Low/Medium.** The idle timer restarts on any chunk, so a client
   that sends a few bytes just inside every 30 s window never trips it. Today an overall limit
   exists only by accident: the Node 22 default `server.requestTimeout` of 300 s. The repo
   does not override it (no `requestTimeout` anywhere in `server/`). That limit is not stated
   in this module, is not tested, and goes away if someone raises it for another route.
   Releases then hand the ticket back for 3 more slow attempts. The holder is a valid,
   authenticated ticket owner with at most 20 open tickets, so this is a bounded DoS on
   connection slots and temp disk, not an open one. Fix: an explicit total body deadline in
   `receiveToFile`, based on `maxSize` with a minimum throughput floor and a hard cap, that
   rejects as `StalledError`. Optionally, do not release after a stall caused by a too-slow
   body. Test it with a stream that trickles below the floor.

4. **uploadTickets.js:210 (`STALL_MS = 3 min`) against legitimate long uploads. Severity:
   Low.** Receiving a 500 MB body plus a store of up to 120 s can take more than 3 minutes,
   so `cms_upload_status` says 'failed' with "Request a new upload URL" while the upload is
   still running. It can later flip to 'done', and the advice makes the client start a second
   upload of the same file. Fix: base the stall threshold on the record's `maxSize`, or on
   a time-of-last-progress field instead of `usedAt`. Alternatively, word the derived state
   as "not confirmed" instead of failed.

5. **uploadReceiver.js:222-226, 278-281: the "can be used again" message is sent even when
   `release()` returned false. Severity: Low.** Once the ticket runs out of releases it is
   failed for good, but the body still tells the client to retry with the same URL. The
   retry gets 403 "not valid". Fix: use the boolean that `release()` returns. When it is
   false, say "request a new upload URL".

6. **uploadReceiver.js:225: the inner `release()` is not guarded. Severity: Low.** If it
   throws (a store error), control goes to the outer catch. That returns 500 "could not be
   stored" for what was a transport failure and calls `release()` a second time. A second
   increment is possible if the first mutate partly applied. Fix: `.catch(log.warn)`, as on
   line 281.

7. **uploadReceiver.js:270-271: `finish(done)` can fail after storage succeeded. Severity:
   Low.** The outer catch then releases the ticket even though an object exists: the record
   has no `asset` yet, so the guard in `release()` does not stop it. A retry stores a second
   object, under a new key until finding 1 is fixed. Fix: set a local `stored = true` right
   after the storage await, and in the catch never release when it is set. Mark it failed
   and log the key instead.

## Checked and fine

- Atomic burn and release through `kv.mutate`, so two PUTs racing for one ticket cannot both
  get past burn.
- A release only happens from `state === 'uploading' && !asset`, never after `done`.
- Each retry runs `peek`, the content-type bind, the `Content-Length` and `maxSize` checks,
  the full `checkAccess` and the storage check again before burning. TTL still applies
  (`burn` checks `expiresAt`).
- A bad file (too large, empty, wrong magic, unsafe SVG, invalid VTT) still spends the ticket.
- Abandoned storage promises: `Promise.race` attaches a handler, so a late rejection is not
  an unhandled rejection. The timers are cleared in `finally`.
- Temp cleanup: `out.destroy()` on fail, then `rm -r` of the mkdtemp dir in `finally` on
  every path. The tests assert no leftovers.
- Release DoS: bounded at 3 per ticket, 20 open tickets per user, and the TTL.

## Resolution
All seven findings applied in the pushed commit (fixed storage key per ticket, abort on storage timeout and no release after it, size-scaled storage and body deadlines, stall threshold scaled to maxSize, single guarded release, no release once stored). Orchestrator verified the gates; no second review round.
