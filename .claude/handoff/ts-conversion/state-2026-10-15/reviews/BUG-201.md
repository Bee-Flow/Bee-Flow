# BUG-201 security re-review: runPolicy.connections 'owner' | 'caller'

- Worktree: `/home/tom/Projects/Bee-Flow-wt/bug-K`, commit `6eb2ce272` (Refs #201)
- Scope: server-side enforcement of the caller-connections mode and the owner decision
  "in caller mode only the starter sees step data"
- Tests: the 27 touched server test files, each run on its own with `node --test`. All
  pass (pass/fail per file: 0 failures).

## Verdict: CHANGES REQUIRED

The core of the change holds up. Identity swap, intersection catalog, admin needs both
sides, fail-closed identity, org match, partial-run policy, resume lock, the sample
payload, and owner-only save/restore are all correct, and the main read paths redact.
What blocks approval: one start path still runs a caller-mode automation as the owner, and
several write routes send back the full run row of a caller-mode run.

## Findings

**F1 (High): a skill linked to an automation starts it with no starter, so a caller-mode
automation runs on the owner's connections.**
`server/core/tools/skillInjection.js:476` calls `executeAutomation` with
`triggerKind: 'manual'` and no `startedByUserId`. `callerOnlyUserId` then returns null,
and `refusesMissingStarter` only covers `studio_app`, `webpage` and `agent_call`
(`callerConnections.js:45`). Result: when another org member activates a shared skill
linked to a caller-mode automation, the run acts in the owner's accounts and its
summary and last output go back into that member's chat. This is the exact case #201
exists to stop.
Fix: pass the asking user (`userId` of `executeActivateSkill`) as `startedByUserId`.
Also invert the safety net: in caller mode, refuse a start without a starter for every
trigger kind except an explicit allow-list of system kinds (schedule, webhook,
app_event, an anonymous form, email). Any future caller that forgets the starter then
fails closed instead of falling back to the owner.

**F2 (High): approving the step of a caller-mode run sends the continued run back
unredacted.**
`server/automation/approvalDecision.js:169` returns `run: newRun`, which carries
`summary`, `error`, `triggerPayload`, `output` and `lastOutput`. The route answers with
that body as-is at `server/routes/automation/approvals.js:335` (assignees, group members,
org admins) and `server/routes/automation/webhooksAndRunOps.js:382` (owner and editors).
Under the lock, the child run is in caller mode.
Fix: `redactRunForViewer(newRun, deciderId)`, done in `decide` or in both routes. Add a
test.

**F3 (Medium): cancel echoes the full run row.**
`webhooksAndRunOps.js:580` and `:584` return `fresh || original` / `updated || original`
to any user with the `act` role. The reject branch of the legacy `POST /runs/:id/approve`
does the same (`run: fresh || run`, around `:646`).
Fix: redact for `req.session.user.id`.

**F4 (Medium-High): a caller-mode run paused on a form page can be read and continued by
someone other than the starter.**
`GET /runs/:runId/form` (`webhooksAndRunOps.js:439`) returns the rendered page, whose
labels and defaults are interpolated from run data, to anyone with `read`.
`POST /runs/:runId/form` (`:462`) lets anyone with `act` answer the page. The run then
continues on the starter's own connections with values another person chose.
Fix: for `isCallerRun(run)`, require `canReadRunData(run, userId)` on both routes. A
different person deciding should go through an approval step, which is built for that.

**F5 (Medium): the one-time notice is enforced only on `POST /:id/run`.**
`routes/automation/runs.js:78` is the only check. Agent calls (in-process and
`/agent-invoke`), studio apps, webpages, logged-in form submissions, partial step runs
and skill starts all act in the caller's accounts without it. Also:
`callerNotice.js:31` calls `collectRequirements` without `loadBlockDefinition` or
`stepProviders`, so providers from call_block bodies and AI-step agents and skills are
left out. The comment there says the walk is "the same" as the pre-check, and it is not.
The seen-row never expires when the definition later adds a provider. `POST /run` reads
the raw row, while `GET` reads the live copy.
Fix: check the notice in one central place for every interactive start, or record the
owner's decision that only the Run button asks. Give the notice the same lookups as the
pre-check, and key the seen-row to the provider set, or reset it when that set grows.

**F6 (Medium, needs an owner decision): sinks the owner controls receive caller-run data,
which the owner can read back.**
- `execKnowledgeWrite.js:152`: ingests into the knowledge base as `ctx.userId` (the owner).
- `datatableResolve.js:64-99` and `datatableWrites.js:165`: write tables in the owner's
  scopes.
- `execFillDocument.js:250` and `execPresentation.js:226`: with `saveCopy`, save into the
  owner's document library.
- `execDocument.js:307`: generated files stored under the owner's key, served to
  approvers and form sessions.

The flow author chose these sinks, but the result contradicts "only the starter sees
outputs".
Fix options: in caller mode, refuse at pre-check or redirect to the caller's scope. At
minimum, name these sinks in the caller notice.

**F7 (Medium, fails closed): App Studio action sequences and app connectors never name
the starter.**
`appStudio/actionExecutor/automationBridge.js:350` and `appStudio/connectors/runners.js:124`
start runs with `triggerKind: 'studio_app'` and no `startedByUserId`. Every caller-mode run
from these paths is therefore refused (`caller_identity_unavailable`). Only the
`studioAppsRun.js` direct route was fixed.
Fix: pass the server-side viewer (`ctx.viewerId` / `viewerId`) as `startedByUserId`. Add
tests.

**F8 (Low): the owner-only rule is enforced per route, not at the store.**
`ownerOnlyRefusal` and `connectionsChanged` run in `crud.js` PUT and in `versions.js`
restore. Other definition writers do not check them: project package install, patch and
upgrade, stage prepare and compensate, and the evolution apply and rollback
(`evolution.js:155` restores an earlier version without comparing
`runPolicy.connections`). The builder tools cannot set runPolicy.
Fix: compare `runPolicy.connections` in `updateAutomation` when the actor is not the
owner, or audit these paths. At least make an evolution rollback keep the current
connections value.

**F9 (Low): run-row redaction is a deny-list.**
`callerRunVisibility.js:38` nulls five keys. Per CLAUDE.md, such payloads should be built
from an explicit allow-list. A new run column that carries data would travel unnoticed.
Fix: build it the way `redactStepsForViewer` and `projectOrgRun` already do.

**F10 (Low): journey steps are redacted by the head's mode.**
`webhooksAndRunOps.js:201` reads `getRunStepsForChain`, but the decision uses the head
row only. If the policy is switched to 'caller' while a run is paused and a non-owner
starter resumes it, the caller-mode leg's steps are shown to everyone.
Fix: redact per leg using each leg's `connectionsMode`.

**F11 (Low, owner decision): AI-step grounding still reads the owner's memories and
knowledge bases in caller mode.**
`aiStepGrounding.js:85-91` and `:137` put owner memories into a run that only the caller
can see. This already happened for shared runs, but it does not match "acts as the
caller".
Fix: use the caller's memories (or none) in caller mode, and document the KB behaviour.

**F12 (Low): the starter gets no run-end notification.**
`runFinalizeEffects.js:121-131` sends the owner a notice without content. The starter is
the only person who can see the details, and nobody tells them.
Fix: also notify the starter.

**F13 (Low): the shape cache is keyed by the owner on caller output.**
`execIntegrationAction.js:290` stores only the shape (keys and types), but object keys
can themselves be data.
Fix: key it by `toolIdentity(ctx).userId`.

**F14 (Info): the notice table has no FK on users.**
`automation_caller_notices.user_id` has no FK, so rows remain after a user is deleted.
Harmless. Optional cleanup in the user purge.

## Round-3 findings

**R3-1 (Medium): an automatic evolution rollback, and package upgrade/patch, can still
move a caller-mode automation back to the owner's connections.**
`server/stores/automationStore/connectionsPolicy.js:32` returns the update unchanged
whenever `savedByUserId` equals the automation's owner. System writers pass the owner's
id as the actor: `automation/evolution.js:155` (rollback, also run automatically when a
canary regresses) and `:133` (apply), `projects/packaging/upgrade.js:315,334` and
`install/patch.js:50` (`ctx.ownerId`), and the stage writers when `runAsUserId` is the
owner. Concretely: an evolution is applied, the owner then publishes the switch to
'caller', and a canary regression later rolls back to `versionBefore` with `goLive: true`.
The live flow is then silently back in owner mode, and shared users act in the owner's
accounts again. The commit message says these writers keep the stored value. They do not.
Fix: drop the saved-by-owner exemption, so that only `allowChange` (passed only by routes
that proved the owner role) may move the mode. Add a test that runs `rollbackEvolution`
over a version with a different mode.

**R3-2 (Low-Medium): `http_request` with `cacheInto` writes the caller-fetched answer into
an owner-scoped table, and the notice does not name it.**
`core/automationRunner/httpCache.js:344,347` resolves the table as `ctx.userId` (the
owner). `DESTINATION_OF_STEP` (`callerConnections.js:114`) only maps the `datatable` step
to `tables`.
Fix: add `dest:tables` when `node.type === 'http_request'` and `node.cacheInto?.datatableId`
is set. Also consider resolving the table as `toolIdentity(ctx)` in caller mode.

**R3-3 (Low): the acknowledgement stores the set computed at POST time, not the set the
person was shown.**
`routes/automation/runs.js:202-203` recomputes the items when the person confirms. If the
definition grows between GET and POST, the new item counts as acknowledged without ever
having been shown.
Fix: the client sends the items it displayed; the server stores the intersection with the
current set, or answers 409 when the two differ.

**R3-4 (Low, functional, fails closed): test runs can loop on the notice.**
`POST /:id/run` with `test: true` judges the notice on the working copy (`runs.js:78`).
The runner does the same. The acknowledgement stores the live copy's items (`:202`). When
an editor who is not the owner adds an app that exists only in the working copy, the
confirm never satisfies the check.
Fix: for a viewer with `edit`, acknowledge the union of the live and working-copy items,
or pass the `test` flag to both notice routes.

**R3-5 (Medium, functional, needs an owner decision): logged-in public-form submitters are
locked out of caller-mode forms.**
A logged-in submitter starts the run as themselves (`formQueueWork.js:62`), so the runner
requires their acknowledgement. The only way to give it, `POST /:id/caller-notice/seen`,
needs the `run` role on the automation, which an ordinary form visitor does not have. Such
a visitor's run therefore always fails with "open this automation once…", while an
anonymous visitor goes through on the owner's connections. A logged-in visitor from
another organisation is refused by the org match. Safe (it fails closed), but the form
then breaks for exactly the logged-in audience.
Fix options: show the notice and record the acknowledgement inside the form flow (scoped
to the form session), or run a public form as a system start unless the form is
members-only. Record the decision.

**R3-6 (Low): per-leg redaction falls back to the head on a read error.**
`routes/automation/webhooksAndRunOps.js:202` does `getRunsInChain(...).catch(() => [])`.
If that read fails, every leg is judged by the head. For an owner-mode head with a
caller-mode later leg, this fails open.
Fix: let the error propagate. Or, when the legs are unknown, hide every step whose
`runId` is not the head's unless the viewer can read the head's data.

**R3-7 (Info): the notice does not list saved HTTP credentials.**
`itemsOf` (`callerNotice.js:25`) uses providers and destinations, not
`httpConnections`. These are org credentials the caller must already be authorised for,
so the risk is low, but the notice says "which of your connections it uses".
