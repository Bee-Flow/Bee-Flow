### Findings

1. **`server/agents/notebooks/notebookAiShield.js:51,61`, medium (licence gate, not a privacy leak).**
   The notebook AI action reads the raw `org_privacy_shield_<org>` row and passes it to
   `composeScan` as `orgShield`. `composeScan._action` reads `piiDetectionAction` directly, so a saved
   `tokenize` is still honoured on a tier without `pii_tokenize`. The resolved shield (`resolved`,
   line 52) is already in hand. Fix: pass `resolved` to `composeScan`. Keep reading
   `storedShield` only for `failClosed`, or take `dlpFailureMode` from `resolved` as well. Add a case to the
   notebook AI shield test: community org, stored `tokenize`, expect block.
2. **`server/routes/ai/directChat/attachmentScan.js:32`, low/medium (same class).** In the
   super-admin fallback the attachment scanner gets the raw sole-org row
   (`shield = allCfg[key]`), and `attachmentScanner` honours its `piiDetectionAction`. The input-text
   twin (`directChat/inputShield.js:84`) already resolves it with `resolveOrgShield(soleOrgId)`. Fix:
   do the same here (resolve the sole org's shield, and use the raw row only when resolving returns null, as
   `inputShield.js` does).
3. **Commit trailer of 448fa709f, `Fixes #261`.** Once 1 and 2 are fixed, `Fixes` is acceptable:
   the issue offered "either the docs or the code should change". For `guardrails_dlp` the docs now
   describe it as a declared, unenforced reserve flag, and that resolves item 3 of the issue for
   DLP through the docs, provided the owner confirms the choice. The proposed tiers.md/tiers.js comparison test was
   not added. If the owner wants that test, or a real `guardrails_dlp` gate, the trailer should
   be `Refs #261` with a follow-up issue. As pushed, with the gaps in 1 and 2, the issue is not fully
   fixed, so: `Refs #261` now, and `Fixes` on the fix-up commit.

### Non-blocking notes

- **Personal shields** (`resolveUserShield`, `orgShield.js:560`) default to `tokenize` and are not
  gated on `pii_tokenize`. This matches the stated scope (the gate is per organisation, and the docs say
  "for the organisation"), but it is an owner decision whether consumer accounts on a Community
  instance may tokenise. Not a privacy regression either way.
- **Instance-level default**: `automationRunner/safety.js:208` falls back to the global
  `aiConfig.piiDetectionAction` without the gate when no org shield exists. There is no target org, so this is out of scope;
  mention it if the docs ever claim instance-wide enforcement.
- **Behaviour change for saved data**: Community orgs with a saved `tokenize` now get `block` in chat,
  attachments and automations. Those runs stop where they used to tokenise. This is the intended
  effect, but it is worth a release note.
- The docs line in `licensing/tiers.md` ("treated as `block` at use time (chat, attachments,
  automations)") becomes fully accurate only after findings 1 and 2 are fixed.

### Checked and fine

- **One entitlement check** (`core/privacy/tokenizeEntitlement.js`) judges the TARGET org through
  `license.hasFeature` (plan grants included), falls back to the tier, and answers `false` on any
  error. The route's `_tierClamps` also fails closed. Covered by the `throwOn: 'feature'` case.
- **Copy, not the cached row**: `resolveOrgShield` clamps `{ ...stored }`, and `applyCustomTypes` reads
  `stored`. A shallow copy is enough because only top-level fields are reassigned (`toolPiiPolicy` is
  replaced, not mutated). Before this commit the shared configStore row itself was mutated. The test
  asserts that the stored row is untouched and that an upgrade brings `tokenize` back. Cache
  invalidation is not needed because the row never changes and the licence is read on every resolve.
- **GET** deep-clones before clamping, so the stored row stays untouched. **PUT** clamps to `block`, persists it and reports
  `clamped_fields`. Clamping instead of rejecting is acceptable: the result is stricter, visible to the
  admin, and the same as the existing `web_search_guard` handling.
- **Downgrade direction**: `tokenize` becomes `block`, and nothing else is rewritten. `block` refuses the request or
  step instead of sending text, so personal data never reaches an LLM unprotected because of this
  change. `synthesizePrivacyFields` and `attachmentScanner` read the clamped `piiDetectionAction`
  first, so a `dlpMode: auto_redact` row cannot re-open tokenising on the main paths.
- **Main use paths** go through `resolveShieldFor`/`resolveOrgShield`: direct chat input
  (`inputShield.js`), direct chat attachments (normal path), agent runtime (`chatWithAgentPrep.js`,
  `guardrailsRunner.js`), notebook chat (`notebookChat.js:198`, which is also `docShield` for scans and
  the tool loop), and automations (`safety.js` via `resolveOrgShield`). The memory scrub paths read the raw row
  only for `enabled`; they always tokenise memory context, which is defence in depth and not the licensed
  action.
- **Docs and `beeflowSite.js`** contain no prices. The counts match the registries: GDPR 25, AI Act 8,
  ISO 27001 25 (58 in total), Compose profiles 5 (`ALL_PROFILES`), and the GDPR article list matches the
  check files. The AGPL "working toward" claim and the Kubernetes-manifests claim are removed.
  `guardrails_dlp` / `audit_log_export` are described as reserve flags, which matches the code (no
  consumer outside `tiers.js`).
- **Tests**: `node --test core/privacy/orgShield.tierClamps.test.js` and
  `node --test routes/orgPrivacyShield.clamps.test.js` both pass (run one at a time).
