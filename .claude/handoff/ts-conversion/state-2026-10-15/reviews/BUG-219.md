# Review BUG #219 (Opus, read-only)

Commit f7259b842 "fix(cms): locale overrides follow their item when an array is reordered".
Tests: `node --test stores/cmsStore.overrideAlign.test.js` 5/5, `stores/cmsStore.locale.test.js` 6/6.

## Verdict: CHANGES REQUIRED

The pure re-keying (`realignOverride`) is right for the case it tests: all items carry distinct
ids, nested id arrays follow their parent, id-less arrays keep index semantics, short overrides
give `null` slots that `mergeLocaleContent` treats as "no translation". Site scoping is fine:
the site query filters with `startsWith(prefix)`, and the page query is keyed by
`cms_project_{siteId}_page_{pageId}` (CMS keys are instance-wide, with no org dimension, as
before). Every server write path that can reorder goes through the hook: admin `PUT site` / `PUT page`,
MCP `cms_update_site_settings`, `cms_update_header_nav`, `cms_update_block`, blog settings
(all via `setProject` / `setPage`). Import, duplicate site and createPage write a NEW site/page
(`previous` is null, so no re-key), and publish only reads. `mutateProject` callers do not
change header/footer order (`removePage` only strips page refs).

The open problems are below. Two of them (1, 2) make the fix lose translations that the old
index behaviour kept, and one (3) means the main editor flow brings the original bug back.

## REQUIRED

1. **HIGH: freshly minted ids drop every translation.** `server/stores/cms/overrideAlign.js:45-50`
   re-keys as soon as prev and next both carry ids, and maps an unmatched next id to `null`.
   `sanitizeNavEntry` / `sanitizeNavDropdown` (`server/cmsBuilder/builderTools.js:618`, `:657`)
   mint a new `nav_` id for every item sent without one. The `cms_update_header_nav` schema
   (`server/cmsBuilder/schemas.js:242`) documents children and mega items as `{ label, link }`,
   with no id field. So a normal MCP header-nav call re-mints every child, mega column and mega
   item id, and the re-key wipes all their translations in every locale. The old index behaviour
   kept them. The same happens to top-level items when a client omits ids.
   Fix: give unmatched slots a positional fallback. If `next[i].id` is not in prev, and
   `prev[i].id` is not in next either (the item was replaced in place), keep `override[i]`.
   At minimum, re-key only when at least one id matches, and use index semantics otherwise.
   Also add `id?` to the children and mega-item schemas and tell clients to reuse the ids.
   Test: a nav whose children come back without ids keeps its NL child labels.

2. **MEDIUM: delete-then-undo loses the translation for good.** In `overrideAlign.js:47-49`, a
   removed item's override entry is dropped when the save lands (the editor autosaves after
   800 ms). Undo, re-adding the item, or moving it to another array (a footer link to another
   column) brings the item back with no translation. Before this change, undo restored the old
   alignment. Fix: keep orphaned entries keyed by id (for example `_orphans: { [id]: entry }`
   on the override, read back when the id reappears in that array), or record this as an
   accepted limitation in the commit and in a test. Do not leave it silent.

3. **HIGH: the editor writes the stale alignment straight back.** The client keeps its locale
   overrides in memory (`localeOverridesRef`) and never reloads them after a page or site save.
   `useCmsAutosave.ts` sends the whole override object on every translation edit. After a reorder:
   (a) translate mode shows the swapped translations until the page is reloaded; (b) the next
   translation edit in the same tab PUTs the old-aligned override over the re-keyed one, which
   restores the bug. The existing warning toast tells the user to "review them in translate
   mode", which is exactly that flow (`agent-hub/.../panel/useCmsContentMutations.js:35-47`).
   This is the same tab, not just a stale second tab as the commit note says. Fix: return the
   re-keyed overrides from `PUT page` / `PUT site` (or reload them after a save that reordered)
   and replace `localeOverridesRef`. Or run the same `realignOverride` on the client in
   `updatePage` / `updateSite`. Then drop or reword the D4 warning (`translatable.js:231-238`,
   `useCmsContentMutations.js:35-47`), which now says something that is only half true.

4. **MEDIUM: the content write and the re-key are not atomic.** `pages.js:65-68` and
   `overrideAlign.js:132-136` read `previous`, write the content, then read, modify and write each
   override with plain `setConfig` (`overrideAlign.js:67-68`). None of this is locked or in a
   transaction.
   - Two saves of the same page or site in parallel both re-key from the same `previous`, so the
     second permutation is applied to an already re-keyed override.
   - The autosave batch runs the page PUT and the page-locale PUT in parallel (`Promise.all` in
     `useCmsAutosave.ts`). Either the client's override overwrites the re-keyed one, or it gets
     permuted a second time.
   - If the re-key throws after the content write, the client retries the batch. `previous` now
     equals the new order, so the overrides stay misaligned for good.
   - A publish that lands between the two writes snapshots new content with old overrides.

   Fix: do the content write and the re-key in one `withTransaction`, taking the
   `pg_advisory_xact_lock` on the content key first (the pattern of `configStore.mutateConfig`),
   reading `previous` inside it, and then locking and rewriting each override key in the same
   transaction. At minimum, write each override with `configStore.mutateConfig` and take
   `previous` from a `mutateConfig` on the content key. `setPageLocaleOverride` /
   `setSiteLocaleOverride` must take the same lock.

5. **MEDIUM: the arrays named in the issue (FAQ, features, chips) are not covered, but the commit
   says they are.** Block array items have no ids (`cmsDefaults.js:432-437` faq items; the editor
   `makeNew` for faq/features/techStats/testimonials/compare/security mints none; only header,
   footer and roadmap mint ids). So `indexById` returns null, and a reorder of these still swaps
   translations silently. The test passes only because it adds synthetic ids. The issue's
   fallback ("at least return a validation warning") is not implemented either. Fix: mint ids
   for block array items (in the sanitizer, with a lazy backfill on read, so the first reorder
   is followed), or have `setPage` return a `validation` warning when an id-less array that has
   overrides is reordered (the server version of `detectArrayReorder`), and surface that warning
   from `cms_update_block` / `cms_reorder_*`. Correct the commit message and the header comment
   of `overrideAlign.js`.

## Optional

6. `overrideAlign.js:45`: duplicate ids in `next` (an item copied together with its id) give
   both copies the translation, and the next save falls back to index semantics because
   `indexById(prev)` now sees the duplicate. That is acceptable, but cover it with a test.
7. `overrideAlign.js:79-82`: the page query uses `LIKE` with `_` wildcards and, unlike the site
   query, no `startsWith` filter. Add the same `startsWith(prefix)` check for symmetry.
8. Each page save now costs one `LIKE` query plus one fresh read per locale, even when nothing
   moved. Skip this when `detectArrayReorder(prev, next)` and a removal check both come back
   negative.
9. Tests to add: concurrent `setPage` against `setPageLocaleOverride`; header children with
   re-minted ids (finding 1); a mixed array (some items with ids, some without).
