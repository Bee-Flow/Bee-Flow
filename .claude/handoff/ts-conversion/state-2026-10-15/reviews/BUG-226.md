## Review of cad3aa76e (Opus, read-only, late round)

### Verdict: CHANGES REQUIRED

The core is right. `writeVersioned` and `mutateProject` check the rev and write inside one
`configStore.mutateConfig` transaction. That transaction holds `pg_advisory_xact_lock(hashtext(key))`
and does the `SELECT` and the upsert on the same client, so two writers can never both pass the
check. A thrown 409 rolls the transaction back. `mutatePage` re-reads fresh, hands the change a
private clone and retries only on `cms_conflict` (5 attempts). Every change function in
`builderTools.js` (SEO, add/update/remove/reorder blocks) and in `updatePageMeta` is pure on its
input. Block ids are minted outside the closure, so a retry inserts the same ids. Update throws
when its block is gone, and reorder keeps blocks added meanwhile. The chrome-only `PUT /site`
(`SITE_CHROME_FIELDS`) closes the orphan-page path from the issue. Page reorder, homepage switch
and page meta already used their own endpoints (`/pages/order`, `/pages/:id/homepage`,
`/pages/:id/meta`), and the sitemap "Show in nav" toggle only changes `header.nav`, so no UI
depended on `pages`/`homepageId` in `PUT /site`. The AI-turn undo now restores the index through
those endpoints. The projects-index touch is under the index lock. The zod envelope
(`z.record`) lets `rev` through. Legacy documents without `rev` read as 0 on both sides
(`revOf` on the server and in `cmsRevisions.ts`). In-repo HTTP writers of `PUT /pages/:id` and
`PUT /site` are only agent-hub (autosave, AI-turn undo, sitemap nav toggle), and all three send a
rev. MCP tools, seeders, import and duplicate go through the store (`mutatePage`/`mutateProject`
or a new-key `setConfig`), so the 428 cannot hit them. The 409 handling in autosave (do not keep
the batch, record the revs of the other answers) is correct, and the save queue serialises flushes.

### REQUIRED

1. **MEDIUM: a versioned write recreates a page deleted meanwhile.**
   `server/stores/cms/revision.js:64` skips the check when the stored doc is missing. So when
   `mutatePage` reads a page, `removePage` deletes it, and the write then lands, the PageDoc is
   recreated as an orphan row that the site does not list. A `PUT /pages/:id` racing a delete does
   the same: the `requirePageInSite` check from #232 runs outside the lock. Fix: when
   `expectedRev !== undefined` and `cur` is not a plain object, throw (a 409, or a 404
   `page_not_found`). Nothing legitimately creates a PageDoc through a versioned write. Test:
   delete between read and write, then assert that no row is written.

2. **MEDIUM: chrome edits that do not bump `rev` can still be overwritten silently.**
   `renameProject` (`server/stores/cms/projects.js:258`) and `removePage` (`:583`, which strips
   header/footer links to the deleted page) change chrome fields through `mutateProject` without
   `bumpRev`. An editor tab with an older copy then saves its chrome at the same rev. That save
   brings back the old name, or a nav link to the deleted page, which is the lost-update class this
   issue is about. Fix: `bumpRev: true` in `renameProject`. In `removePage`, bump only when
   `stripPageRefsToDeleted` changed something. Both editor flows already call `reloadPayload()`
   afterwards, so the acting tab picks up the new rev.

3. **MEDIUM: an editor that is open during the deploy cannot save, with no soft path.** Old SPA
   bundles send no `rev`, so every autosave gets a 428, and Retry fails the same way. The only way
   out is a reload, which drops the edits typed since the deploy. The desktop client also loads the
   SPA from the server and is affected the same way. Suggested fallback for one release: when
   `rev` is missing, write without the check (the old behaviour; `PUT /site` still ignores
   `pages`/`homepageId`, so the orphan-page fix holds), and log a `log.warn` with route and site id
   only. Make the 428 hard in the next release. If the owner accepts the hard 428, at least make
   the old client's error say that the page must be reloaded and that unsaved edits should be
   copied first.

4. **LOW: the editor's own meta save can make its next block save a 409.**
   `updatePageMeta` bumps the PageDoc rev when slug or title change (`mutatePage`).
   `savePageMeta` then relies on `reloadPayload()`
   (`agent-hub/src/components/admin/product-website/panel/useCmsPageMeta.ts:62`), but that call
   bails out when new edits are pending. The pending page save then carries the old rev, and the
   user sees "changed elsewhere" for a change they made themselves. Fix: have `PUT /pages/:id/meta`
   return the PageDoc rev it stored, and record it in autosave's `savedRevsRef` (expose a
   `noteSavedRev(siteId, key, rev)` from `useCmsAutosave`).

5. **LOW: no test for the rewritten AI-turn undo.** The code in
   `useCmsBuilderBridge.ts` (`fetchSiteState`, `fetchPageRev`, restoring the index through
   meta/order/homepage, re-stamping the revs locally) is new behaviour with no test. Add a vitest
   with a mocked fetch: the turn created one page and reordered two, and undo sends the expected
   PUTs with the current revs.

6. **LOW: `refreshSite` still reads through the cache** (`server/cmsBuilder/builderTools.js:152`),
   which the issue named. Use `getProject(siteId, { fresh: true })`, so a turn's page-index
   checks (`findIndexEntry`) see a page that another replica created.

### Merge plan with #219 (`ts-bugs/wip-X2`)

The two approaches compose. Both serialise on the same advisory lock
(`hashtext(projectKey)` / `hashtext(pageKey)`). They must not stay two separate transactions,
and neither may nest inside the other.

- **Never call `mutateConfig(key)` inside `withConfigGroup(key)` (or the other way round).**
  They run on different pool connections, so the inner call waits for the advisory lock that the
  outer transaction holds, and it waits forever.
- `pages.js`: keep X2's `writePageAligned`, and move the rev check and bump into its group:
  `const previous = await io.get(key); if (expectedRev !== undefined && (!isPlainObject(previous) || revOf(previous) !== expectedRev)) throw conflictError('page'); await io.set(key, { ...sanitized, rev: revOf(previous) + 1 });`,
  then the realignment. Drop `writeVersioned` for pages, or let it take an `io`. `setPage` returns
  `{ page: {...sanitized, rev}, dropped, localeOverrides }`. `mutatePage` stays as it is (a retry
  re-runs the whole group, and a 409 rolls back the realignment too).
- `projects.js`: take X2's `withConfigGroup` body for `mutateProject`, and add C2's
  `expectedRev`/`bumpRev` check right after `io.get`. `setProject` goes through
  `writeSiteAligned` with the same check. Keep C2's `updateSiteChrome` and the locked
  `touchProjectsIndexEntry`; X2 still has the old unlocked one. `sanitizeSite`,
  `sanitizePageIndexEntry` and `migrateSite` now live in `stores/cms/siteDoc.js`: apply X2's
  `normalizeStoredSlug` change there. `removePage` moved to `pageRemoval.js` in X2: apply finding
  2 (bump only when chrome changed) there.
- Routes: `putPage` and `putSiteDoc` keep the rev handling and the `HttpError` rethrow, and also
  return X2's `localeOverrides`.
- Testkit: X2's `withConfigGroup` fake and C2's in-memory `concurrency.test.js` harness must both
  support the merged path. Add one concurrency test that runs a stale-rev `PUT` against a block
  reorder and asserts that neither the page nor its locale overrides changed.
- Order: merge X2 first (it is the wider change to the write path), then rebase C2 onto it. Then
  run `concurrency.test.js`, `cmsStore.overrideAlign.test.js`, `configStoreGroup.test.js` and the
  route tests, one file at a time.
