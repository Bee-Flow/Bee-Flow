### Verdict: CHANGES REQUIRED

Publish is right. One parameterised `SELECT ... WHERE key = $1 OR key LIKE $2 OR key LIKE $3`
(`server/stores/cms/publishing.js:50`) reads the site doc, the pages and the overrides from a
single statement snapshot, which bypasses the replica cache. Pages are taken only for entries
in `site.pages`, by exact key. Override keys are classified with literal `startsWith` on the
infixes. The `rev` field is left out of the published pages, and the test checks both the
stale-cache case and that `rev` is absent. Scoping: the base key embeds the validated site id
(`assertSiteId`), and the hex alphabet of ids means the unescaped `_` wildcards cannot reach
another site's keys. Any wildcard over-match would be dropped anyway by the exact-key and
`startsWith` filters. The swallowed `afterPublish` and analytics errors now `log.warn` with
`e.message` only, so no body or personal data goes into the log. `requirePageInSite` gives the
404 for `PUT /pages/:id` and `PUT /pages/:id/locale/:locale`. `assertLocale` in both store
setters closes the `_locale_` key-parsing ambiguity. The MCP override tool already validated the
locale before calling the setter.

### REQUIRED

1. **MEDIUM: import now fails halfway on a non-canonical locale, and leaves orphan rows.**
   `restoreLocaleOverrides` (`server/stores/cms/importSteps.js:298`, `:310`) passes bundle locales
   to the setters unchanged. With the new `assertLocale`, a bundle with `"pt-BR"`, `"NL"` or
   `"nl_NL"` (a hand-edited bundle, or another tool's export) throws. By then `importSite` has
   already written the site doc and all pages, but not the projects-index entry, so the rows are
   orphans and the user sees a failed import that used to work. Fix: in `restoreLocaleOverrides`,
   lowercase each locale, skip any that is still invalid, and add a warning
   (`Skipped translations for an unrecognised language code`) instead of throwing. Test: a bundle
   with one `NL` and one invalid locale imports, with the `nl` overrides and one warning.
   `duplicateProject` (`projects.js` locale loop) copies stored keys, which the routes always
   lowercased, so it is only at risk from older rows. The same skip would make it robust.

2. **LOW: the 404 check is not under the write lock.** `requirePageInSite`
   (`server/routes/cmsPageHandlers.js:25`) reads the site, and the page write happens afterwards.
   A delete that lands in between still lets the write recreate the PageDoc. This is closed for
   good by the store-level fix in BUG-226 finding 1 (a versioned write refuses a missing doc).
   `putPageLocale` has no rev, so it keeps this small window. That is acceptable, but note it in
   the comment.

3. **LOW (nit): escape the LIKE wildcards.** `publishing.js:50` uses `_` from the key infixes as
   a wildcard. It is safe today (see above), but it is fragile if the id alphabet ever changes, and
   the planner can only use the `cms` prefix for an index range. Escape `_`/`%` with a small
   `likePrefix()` helper plus `ESCAPE '\'` (the same approach as `core/dataEngine/queryCompiler.js`
   `likeEscape`), and use it for both patterns. Mirror the change in the test seam regex.

Not blocking: the published `site` keeps its chrome `rev` (pages drop theirs). It does not take
part in the page hash, so the sitemap is unaffected. Strip it too, for consistency, if the
snapshot is ever compared byte for byte.
