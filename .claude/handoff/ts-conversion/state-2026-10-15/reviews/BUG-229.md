# Review BUG #229 (Opus, read-only)

Commit 891dc2202 on `ts-bugs/wip-X2` (`Bee-Flow-wt/bug-X`), "fix(cms): regional locale tags are
served, and unroutable languages are flagged".
Tests: `node --test stores/cmsStore.localeTags.test.js` 3/3, `cms/mcp/dispatch.test.js` 45/45,
`stores/cmsStore.locale.test.js` 6/6.

## Verdict: APPROVE

What I checked:
- The read path now keeps the full tag. `stores/cms/effective.js:110-115` resolves the exact
  override first and then the base language. This is applied to the site override (chrome and
  page titles) and the page override (blocks and SEO) separately, for both the draft and the
  published snapshot.
- `routes/cmsPublicSite.js:60` passes the full tag through.
- Writes were already lowercased and validated against `LOCALE_RE`, both in MCP
  `setLocaleOverride` and in the admin routes (`req.params.locale.toLowerCase()`). So the stored
  key and the requested key agree.
- `cms_set_locale_override` returns a `warning` for any locale outside `LOCALE_PREFIXES`. That is
  accurate: a visitor can only reach `/nl/...`, so `pt-br` and `nl-be` are stored but cannot be
  reached.
- The SSR `?locale=` consolidation in `routes/publicRender.js:378` still collapses to the base
  subtag. That is fine, because it only redirects to routable prefixes.
- The blog read path still collapses (`blogEffective.js:133`, `routes/cmsBlog.js:182`). This is
  documented as left out of scope.

## Recommended (not blocking)

1. The warning does not cover a locale equal to the DEFAULT language (`siteHandlers.js:181`). An
   override for the default language is never applied (`reqLocale !== defaultLocale`). On an
   install whose default is `nl`, an `nl` override reports plain success and is never shown. The
   `en` case on an `en` install gets the generic text. Add a specific warning when
   `locale === defaultLocale`.
2. The public `?locale=` is still not validated (`routes/cmsPublicSite.js:60`). This predates the
   commit, but each request now does up to two config lookups for a caller-chosen tag. On the
   draft fallback path these go through `getConfig`, which also caches misses in an unbounded
   per-process map. Gate the value with `isValidLocale`, cap its length, and fall back to the
   default language otherwise.
3. A regional request can mix sources: the chrome comes from `pt-br` and the page from `pt`, when
   only one of them has an exact override. That is reasonable, but it is worth one sentence in the
   resolver comment.
