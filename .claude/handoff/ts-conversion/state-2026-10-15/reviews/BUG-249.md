### What was checked and is fine

- **No injection into the iframe URL.** `lang` comes from `pageLocale()`
  (`FeatureDemo.tsx:222`), which only ever returns a member of `LOCALE_PREFIXES` or `'en'`. `theme`
  is already clamped to `light|dark`, and `feature` is `encodeURIComponent`-ed and checked
  against the registry. No free text reaches the URL.
- **The override only applies on demo paths.** `demoLangOverride` (`hooks/demoLang.ts:9`)
  returns null unless the path is `/__demo__` or below, and it accepts only a well-formed
  language tag, reduced to its primary subtag. An unknown code falls back through the existing
  available-locales gate in `loadStrings`.
- **It never persists.** With an override, `hasStoredLocale` is false, the initial state ignores
  `beeflow_locale`, the org-default effect (the only other writer in the provider) is skipped,
  and `setLocale` does not write to storage. Elsewhere only `LanguageSwitcher.jsx` writes the
  key, and the demo host does not render it.

### REQUIRED

1. **LOW (process): "Fixes #249" closes an issue that is only partly fixed.** The commit message
   itself says the fixture part (item 3, mixed-language sample data and the per-demo en/nl test)
   is not done. Fix: change the trailer to `Refs #249` and leave the issue open, or open a
   follow-up issue for the fixtures and reference it.
2. **LOW: the "never persists" guarantee has no test.** `demoLang.test.ts` tests only the parser.
   Add a provider test: render `TranslationProvider` at `/__demo__/automations?lang=nl` with
   `beeflow_locale` set to `en`, assert that the locale is `nl`, call `setLocale('en')`, and
   assert that `localStorage.getItem('beeflow_locale')` is still the original value. Assert also
   that no org-locale fetch happens.
3. **LOW: the page language can differ from the language the router resolved.**
   `pageLocale()` (`FeatureDemo.tsx:222`) looks only at the path prefix. The marketing router
   (`App.jsx:272-277`) falls back to `?locale=`, then the stored choice, then the browser
   language for unprefixed paths. So a visitor with a stored Dutch preference on an unprefixed
   URL can get a Dutch page with an English demo. The issue asks for "the locale the marketing
   router resolved". Fix: pass the resolved locale down (a small context or prop from where
   `ProductWebsite` is rendered) and use it here and in `resolveCookieLang`. At minimum, follow
   `resolveCookieLang`'s rule (path, then `?locale=`) so the two agree. If the owner considers
   unprefixed URLs English by definition, record that and drop this finding.
