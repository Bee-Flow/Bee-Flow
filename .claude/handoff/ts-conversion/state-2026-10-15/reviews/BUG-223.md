- Worktree: `/home/tom/Projects/Bee-Flow-wt/bug-Y`, commit `063fa25c0` (Fixes #223)
- Scope: `ensurePublishedSnapshot` now runs before the live id switches (`putSiteLive`,
  `putEnabled`, MCP `cms_set_live_site`), with a 60 s cap and a 502
  `cms_publish_failed`; public `GET /api/cms/site` answers 503 plus a background publish
  instead of falling back to the draft; per-probe and total time limits in
  `utils/mediaDims.enrichMediaDims`.
- Checks run: `cd server && npm run typecheck` (no errors). Tests, each alone with
  `node --test`: `utils/mediaDims` (7), `routes/cmsPublicSite` (9),
  `routes/cmsSiteHandlers` (14), `cms/mcp/dispatch` (45). All pass.

## Verdict: APPROVE WITH REQUIRED CHANGES

The ordering fix is correct and closes the blank-site path: in all three callers the
publish runs first, the live id switches only after it succeeds, and a failure leaves the
previous live site in place. The draft is never served publicly any more. The error texts
are generic (no storage detail, no keys or paths); the underlying message goes only to the
server log. The required items are about the background heal and one place where a probe
does not actually release its socket.

## What holds

- **Ordering.** `cmsSiteHandlers.putSiteLive` (l.144), `putEnabled` (l.179 and l.190) and
  `cms/mcp/publishHandlers` all call `ensurePublishedSnapshot` before `setLiveSiteId`. On
  failure the MCP handler returns before the audit row, and the test checks that the live
  site is unchanged.
- **Two concurrent set-live calls.** No blank state is reachable: each call publishes its
  own site first, then writes the live id, and the last writer wins. Two concurrent
  go-lives of the same never-published site run `publishSite` twice; both writes are
  complete snapshots, so this is harmless (it was already possible through
  `/admin/publish`).
- **Timeout.** On the 60 s cap, `publishSite` keeps running and may still write the
  snapshot, so a retry is quick. The live id is not switched, which is the intended
  behaviour.
- **Background heal guard.** `healing` is keyed by the live site id from config, not by
  anything a visitor controls. It holds at most one entry per site, and `finally` always
  removes it, so it cannot grow without bound. A visitor burst starts one publish per
  process, not one per request. `publishSite` is bounded once the mediaDims budget is in
  place: database work plus at most about 15 s of probes.
- **503.** `Retry-After` is set before the `HttpError` is thrown, and the terminal handler
  keeps it. `getEffectivePublished` returns null only when there is no snapshot (an
  unknown slug on a published site gives `found:false`, not null), so ordinary 404 pages
  do not trigger a heal.
- **Leaks.** `ensurePublishedSnapshot` and the MCP handler expose only `HttpError`
  messages (`expose`). The log line includes `e.message`, but only in the server log.

## REQUIRED

1. **`server/routes/cmsPublicSite.js:21-29`, severity Medium: no cooldown after a failed
   heal.** When the background publish fails (a deterministic publish error, or the
   database or storage down), `finally` clears the guard right away, and the next visitor
   request starts another full publish. A steady stream of visitors then keeps the site in
   a continuous publish loop: every page and override is read again, up to 15 s of storage
   probes run, and every attempt writes a warn line. **Fix:** remember the time of the last
   attempt per site (a `Map<siteId, ts>` in place of the `Set`) and skip a new attempt for
   about 60 s after a failure. Keep the 503 meanwhile. Add a test: two requests after a
   rejected `publishSite` start only one publish.

2. **`server/utils/mediaDims.js:144-149`, severity Medium, tied to BUG-224 F1: the probe
   timeout does not release a request that stalls before its headers arrive.**
   The abort listener is attached only after `await storageStore.streamFile(key)`
   resolves. When `GetObject` itself stalls, `probeWithTimeout` resolves `null` after 3 s,
   but the S3 request stays pending and keeps its pool socket. With the #224 client as
   committed, that lasts indefinitely, because `requestTimeout` only warns. The comment "a
   timed-out probe must give the socket back" holds only for a body that stalls after the
   headers. **Fix:** pass the signal down: `streamFile(key, { range, signal })` into
   `s3.send(cmd, { abortSignal: signal })` (and, in local mode, a check for an already
   aborted signal), and call it from the probe with `{ signal }`. With BUG-224 F1
   (`socketTimeout`) fixed the stall is bounded anyway, but the probe should not rely on
   that. Extend `mediaDims.test.js`: a `streamFile` stub that never resolves sees its
   signal aborted.

3. **`server/routes/cmsShared.js:100` with `cmsSiteHandlers.putEnabled`, severity Low: an
   invalid `siteId` now answers 502 "could not be published".**
   `ensurePublishedSnapshot` calls `cmsStore.getProject(siteId)`, whose `assertSiteId`
   throws a plain `Error` for a malformed id. The catch-all wraps that as
   `cms_publish_failed`. `enabledBody` only checks that `siteId` is a string up to 200
   characters. So a client error is reported as an upstream failure, with a misleading
   message. **Fix:** validate with `SITE_ID_RE` at the top of `ensurePublishedSnapshot`
   (an `HttpError(400, 'cms_invalid_site', …)`), or in `putEnabled` before the call.

## Not required (worth a follow-up)

- **The SPA treats the 503 as "no site".** In `agent-hub/src/App.jsx` (about l.308) the
  code does `r.ok ? r.json() : { enabled: false }`. During the short heal window, a
  visitor on a non-root path is rewritten to `/app`, and `/` shows the static HomePage.
  `Retry-After` is ignored. The window is small and affects only legacy live sites
  without a snapshot. A single retry on 503 (after `Retry-After`, capped) would make
  "the site is being prepared" real for visitors.
- **The 60 s publish cap equals the common reverse-proxy read timeout.** A slow go-live
  can then reach the browser as a proxy 504 instead of the 502 with its message. Now that
  the mediaDims budget bounds `publishSite` to roughly 15 s plus database time, a 30 s
  cap leaves room.
- **Per-process guard.** With several server replicas, each replica can heal once at the
  same moment. That is acceptable (a few publishes, not a herd).
- **Untyped touched files.** `cmsShared.js`, `cmsPublicSite.js` and
  `cms/mcp/publishHandlers.js` still have no `// @typecheck`. This predates the change and
  the commit adds no new files, but the owner rule says to add the marker when a file is
  touched, if it passes the typecheck.
